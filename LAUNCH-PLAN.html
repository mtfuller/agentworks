AgentWorks Launch Plan

Take the AgentWorks runtime from an experimental flag to a public technical preview in seven phases: fix what would break, tell one story, ship a real console, make the positioning true, prove it over days of real work, then tag it.

AgentWorks is a local control layer for the agent CLIs your team already pays for. Give a team of agents shared skills, route work to them, and approve every write or command before it happens, whether the work is code, research or operations.

Starting point

What AgentWorks is today

One Go binary that holds two products. The original artifact toolchain writes skills, agents, MCP servers and hooks once and exports them to Claude Code, GitHub Copilot, Cursor, Gemini CLI and ChatGPT; it is frozen for compatibility. The newer Studio runtime defines teams of agents with shared skills, routes manual, scheduled, Jira and GitHub events to exactly one agent, runs it through the real Claude Code or Copilot CLI, and pauses for your approval before writes and commands. Studio is the product this plan launches.

Verified by running it (5 Oct 2026, commit 03ffb23)

  • Build, gofmt and go vet are clean; the suite passes except one network-dependent test.
  • init --runtime → plan → studio --experimental works on a fresh project.
  • A readwrite run paused for approval in the browser, wrote its file once approved, and recorded the change.
  • Studio rejects foreign Host headers, missing CSRF tokens and cross-origin requests, and sends a strict CSP.
  • Requests above an agent's permission ceiling are lowered; readonly runs that try to write fail closed; duplicate requests create one run.
  • The artifact toolchain scaffolds, validates, tests and exports to three vendors from a fresh project.

Why it isn't launch-ready yet

  • Two runtime bugs would surface under real use or on shared machines.
  • The release gate (soak, dogfood, authenticated runs, sign-off) is empty, so tags are blocked.
  • The README tells the old product's story, and version promises conflict.
  • Studio works but reads as a developer console.

Phase 3 in detail

The Studio console

Studio becomes a single-page console that opens on the approvals queue, because for a control layer that is the product. Everything can be edited through forms, with the underlying file one click away, so people who don't write YAML can run a team.

Proposed console and Studio today

A clickable mockup with sample data, not a working app. Use the sidebar, approve or deny a request, open a run, resolve the inbox, apply a memory change, or edit an agent.

How it's built

  • A small component framework (Preact or Svelte) built with esbuild into internal/studio/static. The compiled output is committed, so go build and go install still need no Node, and CI checks it matches the source.
  • The current CSP stays (script-src 'self', no inline scripts), and every change still carries the CSRF header.
  • New endpoints: GET /api/v1/approvals?state=pending and GET /api/v1/memory-proposals?state=pending. Today approvals are only returned inside a single run.
  • Approval request and decision events join the existing event stream, so badges and browser notifications update live.
  • Playwright smoke tests drive the fake harness through approve, deny, memory and inbox flows in CI.
